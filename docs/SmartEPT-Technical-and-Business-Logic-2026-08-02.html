1. System architecture & how the three parts talk

SmartEPT is deliberately split so the money/licensing plane and the operational/monitoring plane never mix. This is what makes both the SaaS and on-premises editions possible from one codebase, and it is the technical foundation of the "your data stays yours" promise.

Business engine

Central (Superadmin)

Ametecs-hosted. Issues & renews licences, signs offline .lic files, runs GST billing, orders, pay-links, dunning, tenants, the client self-service portal, and installer downloads.

The brain + console

Product (smartept)

One instance per client (cloud tenant or on-prem). Holds all employee/monitoring data, the policy engine, scoring, attendance, reports. Phones Central once a day with licence metadata only.

The sensor

Agent (desktop)

On each employee PC. Visible, consent-gated. Streams attendance/activity/usage/screenshots to its own Product instance — never to Central.

Cloud and on-prem are the same architecture with a different hosting location.

2. Part A — Product (smartept)

2.1 · What it is & why it exists

The Product is a Laravel 11 API + single-page admin console (the admin.blade.php "Ocean Teal" SPA). It is the system of record for everything about a client's workforce monitoring: who works where, on what policy, what they did, and how it scored. Every client gets their own instance (a cloud tenant or an on-prem deployment); a company row (companies) tenants all data and a global scope binds every query to it.

2.3 · The Policy Engine — safe by default

PolicyResolver is the heart of the Product. For each employee/device it walks the assignment precedence DEVICE › EMPLOYEE › TEAM › DEPARTMENT › BRANCH › COMPANY (most-specific wins), resolves each of the 12 policy types, and composes them into the single "bundle" the agent obeys.

  • Safe by default: a device with no applicable assignment gets an empty bundle — tracking disabled. Nothing is ever captured that a policy hasn't explicitly enabled.
  • Tracking-mode override (full / attendance-only / paused) resolves at the most-specific level and is also written into the policy flags, so even a server-side consumer that ignores the mode flag still stops capturing.
  • Resolved cadence surfaced: the screenshot policy exposes effective_interval_seconds + a version, so the agent schedules on the real value and stamps every shot with the policy id/version it obeyed (this is what fixed the "a shot every minute" bug).

2.4 · The Status state machine — one authoritative "what are they doing right now"

StatusService + the status_timeline table are the backbone that fixed a whole cluster of duration/consistency defects. The timeline is an ordered stream of non-overlapping segments with exactly one open segment per employee. Every transition runs inside a DB transaction with a row lock, so two events arriving together can never open two segments.

RuleBehaviour
IdempotencyA repeated event_uuid is a no-op (returns the existing segment).
Heartbeat dedupeSame state (and same meeting) as the open segment → no-op.
Ambient guardBackground ACTIVE/IDLE may not clobber an open manual break/meeting — only an explicit resume or a forced idle (lock/display-off/suspend) may.
Exclusivity (D1)A manual break/meeting started while a different break/meeting is open throws a conflict → HTTP 409. This is why "two breaks at once" and "break + meeting together" can no longer happen.
Forced idleOverrides a MEETING but respects a manual break (you are still on lunch even if the screen locks).

Every dashboard card, widget and report reads this one definition — so live status, durations and history always agree.

2.5 · Attendance derivation — raw punches → the day's sheet

AttendanceDerivation turns raw biometric punches + agent login sessions into the derived daily attendance summary. It is payroll-feeding, so the rules are strict and auditable:

  • Raw stays raw — biometric logs are never mutated; only the summary row is written, with provenance columns showing how each value was derived.
  • Shift-aware checkout (B7): an intermediate OUT (lunch, a walk to the floor) is not a checkout. Checkout = the trailing OUT (the last OUT with no later IN), reconciled with the agent's real logout. A mid-day door OUT can never create an early checkout again.
  • Configurable late (B8/D2): effective arrival is chosen per the company's late_arrival_source — agent login, biometric IN, later-of-both, or shift. Biometric-only employees now get late minutes too. Late is write-once: re-login never moves it (first arrival wins).
  • Idempotent: re-running on a day (delayed punch, re-sync, nightly) converges to the same summary. Never overwrites an approved manual (HR regularization) row unless an explicit reconcile flag is passed.

2.6 · Gate-to-PC — the door punch drives the work day USP

GateService implements the Biometric Gate (Ejaz's design, "Doc 11"). When enabled for a company, an employee's PC agent is walled until the person physically punches in at the door — attaching real-world presence to digital tracking.

  • No IN punch yet → the agent shows the gate wall; status Inactive; ingestion of activity/idle/screenshots is refused (HTTP 423). The agent fails closed.
  • IN punch → gate lifts, work session allowed, status Active.
  • Mid-day OUT while a session is open → automatic "out of office" break (source BIOMETRIC) and the agent soft-locks; the return IN closes the break to the second. Out+in under 2 minutes merges away.
  • Break governance — beyond 45 min raises a compliance event; beyond 3 h HR is emailed.
  • Two switches — biometric_gate (auto/on/off; explicit off = pilot/observe) and gate_enabled (forces the gate on even before a punch device is registered, for API/manual-punch orgs). Companies with no biometric device are never gated — credentials alone start the day.
  • Emergency override — an audited POST /agent-override/gate for admins (door hardware down, etc.).

Residual (D4): absolute tamper-proofing against a full-Administrator user isn't achievable from an Electron/tray app; the server-authoritative gate + exit-lock + tamper logging is the strongest supported protection. A protected Windows service is a separate build if ever required.

2.7 · Productivity & Compliance scoring — the exact formulas

ScoringService::buildSummary() runs server-side (scores cannot be faked at the endpoint) and writes one employee_daily_summaries row per employee/day. Every source is bounded by the company-local calendar day, so cross-midnight events land on the right date and single-timezone installs behave exactly as a plain local day.

Productivity score

present        = active + idle
allotted_break = shift.break_minutes_allowed (or 1h per 9h shift),
                 pro-rated by present / expected-shift
net_working    = present − allotted_break        (min 1s)
productivity % = (active + meeting) / net_working × 100   → clamped 0–100
Worked example. A 9-hour shift with 1 hour allotted break. Priya is present 8h30m (active 6h40m + idle 1h50m), of which 40m was a scheduled meeting. Pro-rated allotted break ≈ 57m (she was present ~94% of the shift). Net working window = 8h30m − 57m ≈ 7h33m. Productive time = active 6h40m + meeting 40m = 7h20m. Productivity = 7h20m / 7h33m ≈ 97%. Idle and violations don't reduce productivity directly — they surface as idle time and in the separate compliance score.

Compliance score

compliance % = 100 − Σ( weight × severity_multiplier )   → clamped 0–100

weight:  AGENT_TAMPER 15 · UNAUTHORIZED_NETWORK 8 · SCREENSHOT_DISABLED 8
         USB_VIOLATION 6 · VPN_PROXY_DETECTED 6 · BLOCKED_APP/WEBSITE 5 · CAMERA_BLOCKED 3
severity multiplier:  LOW 0.5 · MEDIUM 1 · HIGH 1.5 · CRITICAL 2

A "transparent v2" productivity report (reports/productivity-v2) exposes the same numbers as an auditable breakdown alongside the classic report, so a manager can see exactly how a score was built.

2.8 · Roles, reporting hierarchy & multi-tenant isolation

Two independent scopes stack: tenant (a global company scope on every model) and visibility (HierarchyService).

  • Unrestricted roles (Super/Company/HR Admin, Compliance Officer, Auditor) see the whole company.
  • Branch Admin → their own branch only.
  • Manager / Team Leader → their reporting subtree only, computed as a transitive closure over the reporting tree (a manager sees their team leads and everyone under those leads).
  • Employee → their own row only — the single hard scope behind the read-only Employee Self-Service portal.
  • Granular permissions (e.g. meeting.*, audit.export, evidence.view, gate.override) gate individual actions on top of roles; the Roles matrix is fully editable (custom roles).

2.9 · Licence client — the daily phone-home (the hard wall)

LicenseClient validates the installed key against Central once a day (scheduled 01:00) and caches the entitlement bundle. It is availability-first: if Central is unreachable the last cached verdict stands, enforced locally against the bundle's expiry + grace. Only licence metadata + storage-GB is sent — never operational data. The EnsureLicensed middleware is the wall the agent endpoints sit behind.

3. Part B — Superadmin / Central (smartept-central)

3.1 · What it is & why it exists

Central is a mature Laravel 13 B2B licensing + billing platform with three faces: Super Admin (Ametecs staff — tenants, licences, plans, settings, admin users, reports), Admin/sales-support (orders, quotes, invoices, trials, leads, coupons, support desk), and the Client portal (self-service buy/renew, invoices, downloads, tickets, one-click SSO to the hosted console). A public landing + OTP-verified signup + a tokenised pay page complete the funnel. It is the only part Ametecs hosts for every customer.

3.2 · Licensing architecture (RSA-2048, node-locked)

  • Offline .lic tokens are RSA-signed (SHA-256). The private key stays on Central and never ships; the Product verifies with a bundled public key — so an air-gapped on-prem install validates with no call home.
  • Node-locked to the server fingerprint the licence first phones home from; seat cap enforced on device activation; an HMAC check-digit is baked into the key.
  • Server-move path: an admin "reset server fingerprint" action re-binds a licence to a new machine for legitimate migrations.
  • 7-day evaluation and grace windows are part of the entitlement bundle; enforcement is warn-first, hardening to a wall at expiry (per the distribution standard).

3.4 · Order-to-cash & GST invoicing

  1. Quote — admin or client raises an order/quote (PricingService computes it from the bands; optional PO number; coupons applied). Gets valid_until = today + 7.
  2. Pay link — a tokenised /pay/{number}/{token} page (20-char HMAC). Expired links refuse payment (HTTP 410) with a friendly "contact sales".
  3. Gateway — Razorpay or Stripe. Webhook signatures verified with hash_equals, fail-closed when the secret is unset, de-duplicated via webhook_events.
  4. Ledger — recordPayment() is idempotent per payment id, runs in a transaction with lockForUpdate, provisions the licence on the first money/credit event, and settles when the balance is covered. Partial & credit instalments supported.
  5. GST invoice — FY-series numbering issued as MAX+1 under a row lock (deletions can't duplicate); CGST/SGST/IGST split by seller-vs-buyer state; SAC + place-of-supply snapshotted; credit notes for refunds.
  6. Provision — ProductProvisioner creates/updates the tenant's licence & entitlement; the client can SSO straight into their console.

Dunning (RunDunning, daily) sends renewal reminders (T-30/7/1/0), trial reminders (T-3/1/0 → expired), lapsed-licence expiry, and purge windows that keep billing/GST records. Storage governance warns at 90% and pauses screenshots at 100%.

4. Part C — Agent (SmartEPT_agent, desktop)

4.1 · What it is & why it is visible + consent-based

The Agent is an Electron desktop client (no native modules, so npm install && npm start just works) for Windows, macOS and Linux. Its defining principle is visibility and consent: the window stays visible, there is no hidden mode, and the server rejects tracking/media until recorded consent exists where the policy requires it. This is a deliberate trust & legal posture, not a limitation.

4.3 · Consent, gate wall, exit-lock & tamper

  • Consent flow — login → device registration → consent → live status. The server-side policy bundle + recorded consent gate everything.
  • Gate wall — on a gated company the agent shows the wall and fails closed until a synced door punch lifts it (§2.6).
  • Exit-lock — an admin-password exit modal (5 tries → lockout); tamper events (exit/uninstall/service-stop attempts) are reported to the server; an NSIS uninstall guard is built into the Windows installer.
  • Heartbeat every 30s; "today" totals are pulled from the server as the source of truth.

Current version line: agent master v0.11.0 (QA phase). Cross-platform build scripts: npm run dist (Windows NSIS), build-mac.command, build-linux.sh.

5. End-to-end flows

5.1 · An employee's work day

  1. Employee punches IN at the door → biometric sync imports the punch (≤5 min) → Gate lifts.
  2. Agent (consent recorded) starts tracking on the resolved policy bundle; every stamp uses the server clock.
  3. Active/idle, app/website usage, screenshots (if enabled) batch to the Product; a blocked app raises a visible warning + compliance event.
  4. Breaks/meetings flow through StatusService (one open segment, exclusivity enforced); the live dashboard updates.
  5. Mid-day door OUT → auto "out of office" break + soft-lock; return IN closes it to the second.
  6. Night: mark-attendance finalises the sheet (trailing-OUT checkout, late per source), then daily-summary scores productivity & compliance.

5.2 · Buy → licence → run

  1. Lead signs up (OTP) on Central → gets a 7-day trial tenant, or an admin raises a quote.
  2. Client pays the tokenised pay-link (Razorpay/Stripe) → ledger records payment → GST invoice issued.
  3. Provisioner issues the licence; cloud clients SSO into their hosted console, on-prem clients import the signed .lic.
  4. The Product phones home daily (metadata only); entitlement + seat cap enforced locally with grace if Central is unreachable.

6. Distribution & data-ownership model

SmartEPT ships two editions from one architecture, per the Ametecs B2B distribution & licensing standard:

SaaS — Cloud (rental)

Ametecs hosts the client's Product instance; billed per user/month by band; renewals + dunning via Central; one-click SSO. Lowest friction, opex.

On-premises — Perpetual (own it)

Client hosts their own Product instance; one-time licence by user capacity + optional AMC. RSA-signed node-locked .lic runs offline. The client owns their server and their data — Ametecs never sees it.

Client Data Ownership & Perpetual Licence are two of the three headline USPs (with Gate-to-PC). They are not marketing veneer — they fall straight out of the phone-home hard wall and the offline signed-licence design described above.
